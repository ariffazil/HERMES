# Hermes Image Routing

## The Decision Chain

When an image arrives via Telegram gateway, this is the code path:

1. Gateway receives Update with msg.photo
2. Adapter classifies as PHOTO
3. Downloads largest PhotoSize → cache_image_from_bytes()
4. 0.8s batch window (collects rapid single/multi images)
5. `GatewayRunner._decide_image_input_mode()` → `gateway/run.py:15173`
   - Calls `decide_image_input_mode(provider, model, cfg)`
   - Defined in `agent/image_routing.py:418`
6. If `"native"` → images deferred as `_pending_native_image_paths_by_session` → sent as pixels to model directly
7. If `"text"` → `_enrich_message_with_vision()` analyzes images → prepends `[IMAGE TRANSCRIPT]` text → sends TEXT only to primary model

## Config Key Priority

`decide_image_input_mode()` reads **only** `agent.image_input_mode` — the top-level `image_input_mode` is a ghost key.

```yaml
agent:
  image_input_mode: auto          # ← THIS is what the code reads (auto|native|text)

image_input_mode: text            # GHOST KEY — NEVER READ by the routing code
                                  # (stale artifact from old config versions)
```

| `agent.image_input_mode` | Behaviour |
|---|---|
| `auto` (default) | Checks model capabilities + `supports_vision` override |
| `native` | Always sends pixels directly to main model |
| `text` | Always routes through `vision_analyze` auxiliary fallback |

## The `supports_vision` Override Trap

```yaml
model:
  supports_vision: true   # ← OVERRIDES provider metadata
```

**Resolution order** (`agent/image_routing.py:180-207`):

1. `model.supports_vision` (top-level shortcut) — **checked first**
2. `providers.<provider>.models.<model>.supports_vision`
3. Falls through to provider metadata if both are null

### Bug pattern

Setting `supports_vision: true` on a text-only model (e.g. DeepSeek V4 Flash):

```
supports_vision: true
  → _lookup_supports_vision() returns True
  → decide_image_input_mode() returns "native"
  → Image pixels sent DIRECTLY to text-only model
  → Model silently drops or errors
  → vision_analyze transcript path NEVER TRIGGERS
```

**Fix:** Set `model.supports_vision: false` → gateway returns `"text"` → `_enrich_message_with_vision()` fires.

## The Two Text-Mode Approaches

### Approach A: `_enrich_message_with_vision` (CURRENT — active, robust)

Code at `gateway/run.py:10528-10536`:

```python
message_text = await self._enrich_message_with_vision(
    message_text, list(image_paths),
)
```

Flow:
1. Calls `vision_analyze_tool` from `tools/vision_tools.py`
2. `vision_analyze_tool` calls `async_call_llm(task="vision", ...)`
3. `async_call_llm` resolves `auxiliary.vision` config → uses configured vision provider/model
4. Image sent as base64 `image_url` content block to vision model
5. Returns structured SCENE / OCR / DATA sections
6. Prepended as `[IMAGE TRANSCRIPT — generated by vision model, not seen by agent directly]`
7. Primary model receives TEXT ONLY

**Why this is robust:**
- Vision call is isolated — failure produces `[couldn't analyze]` fallback text, never blocks text delivery
- Output is TEXT — EVERY fallback model can process it, no 413 cascade
- Primary model stays unchanged (DeepSeek Flash): stable, proven, coding capability maintained
- No runtime model swap or session identity disruption

### Approach B: Path B model swap (REMOVED — cascade failure)

Previously at `gateway/run.py:10528-10564`. When `_img_mode == "text"`:

```
1. Set _pending_native_image_paths_by_session[session_key] = images
2. Set _pending_vision_model_overrides[session_key] = vision model
3. run_conversation() sees model override → swaps to MiniMax-M3 as full responder
```

**Failure cascade proven 2026-07-30:**
```
Path B: model → minimax-m3 via minimax provider
  ❌ "Authentication failed" / provider error
  ↓
Fallback ke llama-3.1-8b-instant (text-only, no vision)
  ❌ 413 — image bytes still in context
  ↓
Fallback ke openrouter/auto-beta
  ❌ 413
  ↓
Fallback ke deepseek-v4-pro
  ❌ Credits exhausted
  ↓
DEAD. 413. No surviving fallback.
```

**Root cause:** The model override deferred images as native attachments (`_pending_native_image_paths_by_session`), but ALL downstream fallback models are text-only. When the vision provider fails, the image bytes are still in the message, and every text-only model in the fallback chain gets a 413 (payload too large / context length exceeded) because it can't process image data.

## How `_enrich_message_with_vision` Works

Location: `gateway/run.py:15246-15323`

```python
async def _enrich_message_with_vision(self, user_text, image_paths):
    from tools.vision_tools import vision_analyze_tool
    analysis_prompt = (
        "Analyse this image and output THREE sections:\n"
        "1) SCENE: ...\n2) OCR: ...\n3) DATA: ...\n"
        "Rules: Do NOT speculate. Do NOT interpret or infer meaning."
    )
    for path in image_paths:
        result_json = await vision_analyze_tool(
            image_url=path,
            user_prompt=analysis_prompt,
        )
        # Wrap as [IMAGE TRANSCRIPT] block
    # Prepend transcripts to original user_text
```

`vision_analyze_tool` at `tools/vision_tools.py:1063`:
1. Resolves image source (URL or local path) to bytes
2. Normalizes format (SVG/BMP → PNG)
3. Encodes as base64 data URL
4. Calls `async_call_llm(task="vision", messages=messages, ...)`
5. `async_call_llm` → `_resolve_task_provider_model("vision", ...)` reads `auxiliary.vision` config
6. `resolve_vision_provider_client()` builds OpenAI-compatible client for the provider
7. Image sent as `image_url` content block
8. On overflow, auto-resizes and retries once

## Enrichment Prompt Pattern — Identity Extraction (F2 TRUTH)

The enrichment prompt sent to the vision model determines DeepSeek's epistemic floor. DeepSeek is **fundamentally blind** — it only knows the world through Qwen-VL's transcript. If Qwen-VL misses a critical visual cue, DeepSeek's logic will be perfectly sound but factually wrong. This is an F2 TRUTH architectural vulnerability.

**Default enrichment prompt (from code):**
```
Analyse this image and output THREE sections:
1) SCENE: ...
2) OCR: ...
3) DATA: ...
Rules: Do NOT speculate. Do NOT interpret or infer meaning.
```

**Problem:** The "do not interpret" rule means Qwen-VL describes "lelaki sasa dengan medal" instead of "Chris Bumstead, 5× Mr. Olympia." DeepSeek gets a generic description and has to infer identity — which it often hallucinates (F2 violation).

**Recommended injection (to be patched into `_enrich_message_with_vision`):**
```
[VISUAL EXTRACTION — required before answering]
1. Identify ALL individuals (name, known attributes, distinguishing features)
2. Extract ALL visible text (logos, labels, signs, documents)
3. Describe scene: objects, spatial relationships, lighting
4. Note any brand, model number, price, or identifying marks

Then answer the user's question: {user_prompt}
```

**Impact (proven 2026-07-30):** Before patch, Qwen-VL described CBUM as "lelaki sasa, senyum lebar, medal Olympia 2024" → DeepSeek inferred ESTP but didn't know the person. After identity injection, model would identify "Chris Bumstead" directly.

**Architectural constant:** In a PRMT system, Qwen-VL's transcript IS DeepSeek's reality. If Qwen-VL doesn't write it, DeepSeek cannot know it. Language is not the medium — language IS the reality. This is the defining property of decoupled perception-judgment architecture.

MuleRouter (`api.mulerouter.ai`) offers Qwen3-Max and Qwen3-VL-Plus via its `/v1/chat/completions` alias. Could replace OpenRouter as `auxiliary.vision.provider` if:
- Vision quality is verified (Qwen3-Max is a general model — risk of weak vision like MiniMax-M3's rabun issue)
- The unified billing benefit outweighs the vision quality risk

**Current verdict:** Keep OpenRouter for vision — cost is negligible ($0.000014/call) and quality is proven with Qwen VL Plus. See `provider-routing-zen` skill's `references/mulerouter-evaluation.md` for full comparison.

## Auxiliary Vision Config

```yaml
auxiliary:
  vision:
    provider: minimax          # Provider name from config.yaml providers section
    model: minimax-m3          # Vision-capable model name
    base_url: ''               # Empty → inherits from providers.<name>.api
    api_key: ''                # Empty → inherits from providers.<name>.key_env
    timeout: 120               # Vision models can be slow (default 120s)
    temperature: 0.1           # Low temp for transcription accuracy
    download_timeout: 30       # Image download timeout
    max_concurrency: 4         # Parallel vision analysis limit
```

The `base_url` and `api_key` are intentionally left empty — they inherit from the main provider config at `providers.<provider>.api` and `providers.<provider>.key_env`. Do NOT duplicate them unless overriding.

## Common Failure Modes

| Symptom | Root cause | Fix |
|---|---|---|
| `[IMAGE TRANSCRIPT — generated by vision model]` never appears | `supports_vision: true` on text-only model | Set `model.supports_vision: false` |
| 413 cascade to all fallbacks after image send | Path B model swap still active — vision provider failed, image bytes in context | Remove `_pending_vision_model_overrides` code, use `_enrich_message_with_vision` |
| `Authentication failed` on vision provider | `auxiliary.vision.base_url` or `api_key` wrong | Check `providers.<provider>.api` and `key_env` are correct |
| Vision model returns Chinese/garbled response | MiniMax-M3 defaults to Chinese for vague prompts | Ensure analysis_prompt has strict English-output instruction |
| Image download fails in `vision_analyze_tool` | Local file URL not accessible to httpx | `vision_analyze_tool` can take local file paths directly — gateway passes absolute path. Check `_image_url_shape_ok` allows file:// or passes raw path |

## Pitfalls

- **Ghost keys** — Top-level `image_input_mode` does nothing. Only `agent.image_input_mode` is ever read by `decide_image_input_mode()`.
- **`supports_vision` shortcut** — Setting `model.supports_vision` overrides **everything**: provider metadata, model catalog, capability lookup. Must be false for text-only models.
- **`auxiliary.vision` nesting** — Must be under `auxiliary:` (plural), not a standalone `auxiliary:` key.
- **Model swap cascade** — Never defer images as native attachments when the primary model is text-only. If the vision model swap fails, ALL fallbacks get 413. Use `_enrich_message_with_vision` instead — vision is isolated.
- **Empty base_url/api_key** — Leave `auxiliary.vision.base_url` and `api_key` empty to inherit from provider config. Duplicating them creates drift.
- **Timeout too low** — Vision models (especially free/open) can take 30-60s. Set `auxiliary.vision.timeout: 120`.
- **MiniMax-M3 is generation-capable, not understanding** — The MiniMax MCP server (`pipx install minimax-mcp`) only has generation tools (`text_to_audio`, `generate_video`, `text_to_image`, `music_generation`). No `vision_analyze`, `image_describe`, or image understanding tools. The vision-understanding path uses MiniMax-M3 via the OpenAI-compatible API endpoint (not MCP).

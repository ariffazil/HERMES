# Telegram Media Pipeline — Hermes Gateway

> Source of truth: `/usr/local/lib/hermes-agent/plugins/platforms/telegram/adapter.py`
> Routing logic: `/usr/local/lib/hermes-agent/agent/image_routing.py`
> Enrichment: `/usr/local/lib/hermes-agent/gateway/run.py`
> Last verified: 2026-07-30

This document traces what happens when a user sends an image (or other media) via Telegram to Hermes.

---

## 1. Adapter receives the update

`_handle_media_message()` (adapter.py:7961) is the entry point. It:

1. Checks user authorization (`_is_user_authorized_from_message`)
2. Classifies message type via `_media_message_type()` (adapter.py:7332):
   - `msg.photo` → `MessageType.PHOTO`
   - `msg.video` → `MessageType.VIDEO`
   - `msg.audio` → `MessageType.AUDIO`
   - `msg.voice` → `MessageType.VOICE`
   - `msg.document` → `MessageType.DOCUMENT`
   - `msg.sticker` → `MessageType.STICKER`
3. Builds a `MessageEvent` with the caption (if any) as `event.text`

## 2. Image download & local caching

For **photos** (adapter.py:8008-8033):

1. Takes **largest PhotoSize**: `msg.photo[-1]` (Telegram sends multiple sizes)
2. Calls `photo.get_file()` → `download_as_bytearray()` to pull raw bytes
3. Determines file extension from `file_obj.file_path` (default `.jpg`)
4. Saves via `cache_image_from_bytes(bytes, ext=ext)` to local cache
5. Sets `event.media_urls = [cached_path]` and `event.media_types = [mime]`

For **stickers**, `_handle_sticker()` downloads and runs vision description.

For **voice/audio/video/document**, similar download→cache→enrich pipeline (voice → STT transcription, documents → text extraction notes).

### Size limits

- `_max_doc_bytes`: default 20 MB
- `_telegram_media_size_allowed()` checks size before downloading
- Oversized media gets a text note: `[Observed Telegram attachment too large]`

## 3. Batching

Two batching mechanisms to avoid self-interruption on rapid sends:

### Photo batch (single photos, 0.8s delay)
- `_photo_batch_key()`: derived from chat + user + message thread
- `_enqueue_photo_event()`: buffers into `_pending_photo_batches`
- `_flush_photo_batch()`: fires after 0.8s settle window

### Media group (album)
- When `msg.media_group_id` is present, photo is queued via `_queue_media_group_event()`
- `_flush_media_group_event()` fires after 0.8s window
- All photos in a media group become a single `MessageEvent` with multiple `media_urls`

## 4. Enrichment pipeline (`_prepare_inbound_message_text` in run.py ~line 10432)

Once the event reaches the gateway runner:

1. Classifies each attachment by MIME (trusts per-attachment MIME first, falls back to `MessageType.PHOTO`)
2. Separates into `image_paths`, `audio_paths`, `video_paths`, `audio_file_paths`
3. Calls `_decide_image_input_mode()` → returns `"native"` or `"text"`

## 5. Image routing — two approaches

### 5a. Native vision (`"native"`) — when active model supports vision natively

Active model reports `supports_vision=True` (probed from config override or models.dev metadata).

- Images deferred to `run_conversation()` via session-scoped buffer
- Attached as OpenAI-style `image_url` content parts on the user turn
- Provider adapters translate to vendor-specific multimodal format
- Agent sees actual pixels natively

### 5b. Text transcript pipeline (`"text"` — `_enrich_message_with_vision` at run.py:10534)

When `_decide_image_input_mode` returns `"text"` (text-only primary model like DeepSeek V4 Flash):

```python
else:
    message_text = await self._enrich_message_with_vision(
        message_text, list(image_paths),
    )
```

This runs `vision_analyze_tool()` on each image with a strict SCENE/OCR/DATA prompt, using the `auxiliary.vision` provider (MiniMax-M3 via minimax provider). The result is prepended as:

```
[IMAGE TRANSCRIPT — generated by vision model, not seen by agent directly]
SCENE: ...
OCR: ...
DATA: ...
[END IMAGE TRANSCRIPT]
```

**Key properties:**
- The primary model (DeepSeek Flash) receives **text only** — no image bytes in context
- Every fallback path works if the primary call fails (no 413 cascade)
- If MiniMax vision fails → `[couldn't analyze image]` text → DeepSeek still responds
- Single hop, isolated tool call

**The earlier Path B approach (model swap, 2026-07-29) was replaced with this on 2026-07-30** because it had a fatal cascade failure: if the swapped model failed, image bytes were still in context and no fallback model could process them → 413 → compression → 413 → dead.

## 6. Critical config trap: `model.supports_vision`

The config key `model.supports_vision: true` (under the `model:` section, NOT `agent.image_input_mode`) short-circuits the image routing:

```
decide_image_input_mode("deepseek", "deepseek-v4-flash", cfg)
  → _supports_vision_override(cfg) reads model.supports_vision: true
  → returns True immediately
  → decide_image_input_mode returns "native"
  → _enrich_message_with_vision NEVER activates
```

Even with `supports_vision: true` set incorrectly on a text-only model like DeepSeek V4 Flash, the router trusts the config and attaches raw image pixels to an API that can't process them. The model either silently drops the image content or errors.

**Fix:** Set `model.supports_vision: false` (or remove the key entirely) for text-only models. Only set it `true` for models that actually accept `image_url` content.

## 7. `delegate_task` and vision — model inheritance

`delegate_task` subagents **inherit the parent's model**. Spawning a subagent to "analyze this image" still routes to DeepSeek V4 Flash (text-only). The subagent cannot see the image natively.

For delegated vision, the child would need its own model override or access to a vision-capable tool like `mmx vision describe`. The delegation pattern adds complexity (2 round trips, file path passing) without solving the core problem.

## 8. Minimax MCP — generation only, no vision analysis

The official `minimax-mcp` (github.com/minimax-ai/minimax-mcp) provides tools for:
- `text_to_audio`, `list_voices`, `voice_clone`
- `text_to_image`, `generate_video`, `music_generation`
- `voice_design`

It does **NOT** provide any vision/analysis/image-description tools. It is useful for *generating* media, not *understanding* images a user sent. For image analysis, use:
- MiniMax-M3 via the `minimax` OpenAI-compatible provider (auxiliary.vision)
- `mmx vision describe --file <path>` via mmx-cli

## 9. Current federation config (as of 2026-07-30)

```yaml
model:
  provider: deepseek
  supports_vision: false        # MUST be false for DeepSeek V4 Flash
  default: deepseek-v4-flash

auxiliary:
  vision:
    model: minimax-m3
    provider: minimax
    timeout: 120
```

The `minimax` provider points to `https://api.minimax.io/v1` with `MINIMAX_API_KEY` from kunci-mas.env. MiniMax-M3 accepts `image_url` content type natively. Verified 2026-07-30: 1280×720 images processed in ~3s, returns 200.

## 10. Config knobs

| Config key | Location | Effect |
|---|---|---|
| `agent.image_input_mode` | `config.yaml` | `auto` (default), `native`, `text` |
| `model.supports_vision` | `config.yaml` | **TRAP** — declares vision capability; `true` on text-only models poisons routing |
| `auxiliary.vision.*` | `config.yaml` | Vision backend for `_enrich_message_with_vision` transcripts |
| `platforms.telegram.extra.rich_messages` | `config.yaml` | Bot API 10.1 rich message rendering |
| `HERMES_TELEGRAM_MEDIA_BATCH_DELAY_SECONDS` | env var | Photo batching delay (default 0.8s) |
| `HERMES_TELEGRAM_TEXT_BATCH_DELAY_SECONDS` | env var | Text batching delay (default 0.3s) |
